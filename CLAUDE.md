# forktime-outreach

Outbound voice agent + the web app that runs it. The agent phones restaurants about a large-party booking for around 12 to 14 people for an unnamed customer, asks for the owner, qualifies the venue, and explains Forktime's AI call-handling service to qualified owners. Separate from forktime-core on purpose: own repo, own database, own LiveKit agent name (`outreach-agent`), own deploy.

> Update this file in the same commit as any structural change (a new route, event, setting, env var, or rule).

## Product rules (owner + build decisions, 2026-11-21). Do not weaken these.

- **What the call is (owner, 2026-11-21):** the assistant calls about a large-party booking for around 12 to 14 people for an unnamed customer. It never gives, guesses, or implies the customer's name. It can state the group size, but treats their identity, date, and budget as confidential. The opening is: "Hi, this is Sara calling about a large-party booking for around 12 to 14 people. This call is recorded. Is the owner or manager around?"
- **The owner flow (owner, 2026-11-21):** once the agent has the owner or a deciding manager, it asks their name and saves it as `contactName`. It then asks, one at a time: do you take large bookings, roughly how many can you seat, do you have vegetarian or vegan options. A place that takes no large bookings or seats well under 20 gets a warm goodbye (`not_a_fit`), no pitch. Otherwise it says it will call back about the booking after it has the date and final details, then uses the owner's name once to explain that it is an AI assistant from Fork Time: Fork Time finds diners a table and answers restaurant phones. A normal yes is filed as `owner_callback` and receives a follow-up call. It transfers only when the owner specifically asks to speak to someone immediately (`transfer_to_rep`). Answers are filed on the call (`contactName`, `takesLargeBookings`, `seats`, `capacityNote`, `vegetarianVegan`, `interestedInSystem`) and shown in the call panel.
- **Call-backs use caller ID (owner, 2026-11-21):** staff and owners are told to call back on the number this call came from. The agent never says, reads, spells, or repeats the number aloud. The inbound route identifies the caller and carries the earlier call notes.
- **Inbound call-backs** (owner, 2026-11-21): the call-back number is meant to reach this agent. A LiveKit SIP dispatch rule for that number with agent name `outreach-agent` sends the call here (the owner sets up the trunk and rule; nothing in this repo touches telephony). With no call details in the room, the agent reads the caller's number from the phone participant (`sip.phoneNumber`), asks the app (`POST /api/agent/inbound`, agent key), which opens an inbound call record (`direction: "inbound"`, never takes the dialling line) and returns the call's details plus what was noted on the last call to that number (`previousNoteOf`). It opens differently for a known and unknown caller, and carries on from the notes without re-asking answered questions.
- **The Forkmate line (owner, 2026-11-25): every inbound caller we never rang reaches Forkmate, on every number.** A number we dialled (`startedAt` set, a second attempt, or ended: a missed call is re-queued with `startedAt` cleared) is a restaurant calling Sara back and keeps the call-back flow above; anyone else, hidden numbers and repeat Forkmate callers included, gets `meta.mode = "forkmate"` (`lib/inbound.ts`, call record `inboundMode`). Outbound calls are untouched. The agent then uses only `src/forkmate/`: `script.js` holds the owner-approved wording (greeting "Hi, this is {agent}, Forkmate's AI assistant. This call is recorded. Are you booking for a group, or listing a venue?", the booking and venue questions, read-back, consent and closing lines: word for word, change only on the owner's word) and the instructions; `draft.js` decides the next question from what was recorded; `tools.js` gives the model `note_booking` / `note_venue` (record every answer, including ones given before they were asked; the result is the exact next line to say), `save_booking` / `save_venue` (send what was recorded) and its own `end_call` (outcomes `forkmate_booking`, `forkmate_venue`, `not_interested`, `wrong_number`, `other`). **Why the note tools:** with the script alone, Haiku 4.5 (no thinking) asked answered questions again and skipped unanswered ones whenever a caller gave several answers at once (practice runs, 2026-11-25); recording answers and returning the next line from code made 15 of 15 pass twice. Cost: two short model steps on an answering turn (median about 1.1 to 1.6 s of model time in text runs). Saves go to the Forktime API, `POST {FORKMATE_API_URL}/api/forkmate/phone/{enquiries,venues}` with `x-forkmate-key: FORKMATE_PHONE_KEY` (forktime-core backend `forkmate/`): same records, team email and admin page (`/admin/forkmate`, "By phone") as the forkmate.com.au forms; no email is asked for; the spoken consent is required before a save; one call saves one request. If the API can't be reached the agent says so and the call summary carries every answer. Practice runs: `pnpm --filter @outreach/agent sim:forkmate [name]`.
- **The welcome messages are editable in Settings.** Three templates in `settings` (`welcomeOutbound`, `welcomeCallbackKnown`, `welcomeCallbackNew`) with `{agent}` `{rep}` `{topic}` `{recorded}` placeholders are rendered by `renderWelcome` in `apps/web/lib/opening-line.ts`. Blank, unknown placeholder, and invalid-number input are rejected. They are web-side only: changing wording never needs an agent deploy.
- **The Forktime explanation:** the assistant talks naturally about the booking enquiry first. If someone directly asks whether it is an AI, it answers plainly. After a venue qualifies, it explains that it is an AI assistant from Forktime and offers the Forktime service. The group size is around 12 to 14 people; date, budget, and customer identity are never produced or guessed.
- **"What the call is about" in Settings must be suitable for every number in the queue.** The agent says it on every call.
- **A no is a no.** "Not interested" / "stop" from anyone ends the call; "don't call again" puts the number on the do-not-call list.
- Whoever picks up is staff until they say they are the owner or manager; only they are offered the transfer. **Staff get no details and no phone number** (owner, 2026-11-20: "no one can note a number in a busy restaurant"): the agent asks when the owner will be available, files it as `callbackTime`, and the team calls back then, by hand or from the app (`Schedule` on a finished call sets `notBefore`; the queue dials it when due). A scheduled call is only dialled while the queue is running AND something ticks it (an open screen or an agent event): there is no background timer yet. `settings.callbackNumber` still exists but is unused and no longer required to start.
- Calls go out one at a time, inside the calling window, at most `maxAttempts` tries (only an unanswered call is retried).

### apps/web

- `lib/queue.ts` pure decisions (`planNext`, `staleVerdict`, `retryPlan`); `lib/queue-runner.ts` `advanceQueue()` reads the DB, asks them, acts. Idempotent and safe to call from anywhere: the screen calls it every few seconds (`GET /api/queue`), and the agent's "ended" event calls it so the queue moves with no screen open.
- **One call at a time is enforced by the database**: a unique partial index on `calls.active` (`lib/db.ts`). `claimForDial` returns null on the duplicate-key error. Do not replace this with an in-memory lock.
- `lib/dialer.ts` places a real call: LiveKit room (metadata = the call's details) → agent dispatched by name → `createSipParticipant` with identity `callee`, `waitUntilAnswered: false`. Same shape as forktime-core `DemoCallService`.
- `lib/simulate.ts` is the dry run (`DIAL_MODE` anything but `live`): scripted calls advanced by the clock, nothing dialled, calling hours ignored.
- `lib/agent-events.ts` is the ONLY writer for what the agent reports (`POST /api/agent/events`, header `x-agent-key`). Events: `answered`, `transcript`, `stage`, `not_answered`, `ended`, `recording`. An event whose `attempt` is not the call's current attempt is ignored.
- `lib/outcomes.ts`: `AGENT_OUTCOMES` (what the agent may file) + `SYSTEM_OUTCOMES`. `tests/agent-contract.test.ts` fails if the agent's copy drifts.
- Auth: one operator from env (`ADMIN_EMAIL` / `ADMIN_PASSWORD`), signed cookie (`lib/session.ts`, jose), `middleware.ts` guards everything except `/login`, `/api/auth/login`, `/api/agent/events`.
- Settings are one document (`lib/settings.ts`); phone numbers are stored in E.164 and a number that can't be parsed is a validation error, never saved as typed.
- `lib/carrier.ts` lists the Telnyx account's numbers and ElevenLabs voices for the Settings pickers (read-only calls).

### apps/agent

- `src/call.js` `OutreachCall` is one call: wait for pickup (`sip.callStatus === "active"`), start the session, opening line, model conversation, transfer or end, file the call.
- Voice stack values are in `src/config.js` and mirror forktime-core's phone agent: Soniox `stt-rt-v6` (en, strict, `maxEndpointDelayMs` 800, booking key terms as context), ElevenLabs `eleven_v4_turbo` (`pcm_16000`, stability 0.6 only: v4 is a dialogue model), Claude `claude-haiku-4-5` with no thinking, Silero VAD 0.5, endpointing 600/1000 ms, telephony noise cancellation.
- **Turn detection differs from the phone agent**: default `TURN_DETECTOR=stt` (Soniox's own end-of-turn). `multilingual` uses LiveKit's model like the phone agent, but needs its model files (forktime-core restores them with `scripts/restore-turn-detector.mjs`; HuggingFace refuses the JS download).
- **The opening line starts the moment they stop saying hello** (owner, 2026-11-20: "people pick up and say hello hello, they won't hear the welcome"). Three parts: its audio is made while the phone rings (`prepareOpening`, played through `say(text, { audio })`); it is triggered by the voice detector's speaking → listening change, not by the transcript arriving; and if they say nothing it starts 0.9 s after pickup (`TIMING.openingWaitMs`). It is uninterruptible, so a second "hello?" does not cut the disclosure off.
- **Anything said before the opening line has finished is dropped by the SDK** (`StopResponse` in `onUserTurnCompleted` discards the turn; it never reaches the chat history). `onEarlyWords` keeps it: every line goes to the transcript, and the first one is judged (`lineCheck`) and added to the model's instructions (`updateInstructions`, "When they picked up … they said"), so "Luigi's, owner speaking" is not lost.
- **Voice company** (`settings.voiceProvider`, `elevenlabs` | `fishaudio`; owner 2026-11-20: "Fish Audio, the closest to human"). `voiceSetup` in `src/config.js` builds the right plugin options: Fish Audio uses `s2.1-pro`, 16 kHz, low latency, temperature 0.6, and takes the speed natively (clamped to 1 to 1.2, no model switch), exactly as the phone agent does; the key is `FISH_API_KEY` (agent env only). Settings saved before this field exist read back as ElevenLabs. There is no backup voice: if Fish is down, the call is silent.
- **Speaking speed** (`settings.voiceSpeed`, 1 to 1.2; `ttsOptions` in `src/config.js`): v4 Turbo is a dialogue model and takes only `stability`, so the plugin ignores `speed` on it. Normal speed = v4 Turbo; anything faster = `eleven_flash_v2_5` at that speed. Measured on one line with the Canadian voice: 9.4 s on v4 Turbo, 6.8 s on Flash at 1.2. The default voice is `canadian-female-upbeat` (`TgnhEILA8UwUqIMi20rp`).
- **Tools return `undefined`** (`transfer_to_rep`, `end_call`). In this SDK a tool that returns nothing makes the model NOT speak again. The tool only records what was asked (`this.pending`); `runPending` runs on `FunctionToolsExecuted`, after the agent has stopped speaking. Do not `await` speech inside a tool.
- The goodbye rides in `end_call.goodbye` and is spoken by the call itself, because the model often called the tool without saying anything (found in practice runs: it hung up on "not interested" in silence).
- **Who answered** (`src/lineCheck.js`): the first thing heard gets a one-word model judgment (voicemail / menu / person; doubt = person). A recording followed by 4 s of silence after the opening line ends the call (`handleQuietLine`). Asking the model to notice a recording mid-conversation was unreliable.
- Transfer (`src/transfer.js`): the owner stays in the room, the rep is dialled in with a ring tone (`playDialtone`, `waitUntilAnswered: true`), then the agent session closes and the agent stays silent until either hangs up. If the rep does not pick up, the agent says so and takes a call-back time.
- Recording: LiveKit Egress, audio only, to `outreach/<callId>-<attempt>.ogg` in the bucket from `EGRESS_S3_*` (same mechanism as the phone agent).
- A call the model never filed is filed once from its transcript (`src/wrapup.js`).

### apps/api (Phase 1, 2026-11-26; local only, not deployed)

- **Run it:** `pnpm --filter @outreach/api db` (a local MongoDB on 27018 without Docker, data in `apps/api/.data`), then `pnpm --filter @outreach/api build && node apps/api/dist/main.js` (or `dev`). `.env` from `.env.example`; without `RESEND_API_KEY` sign-in codes are printed to the log, and `DEV_LOGIN_CODE` (refused in production) works for any email. `JOBS_INLINE=true` runs jobs in the request (no Redis); production runs `pnpm worker` on BullMQ.
- **Shape:** `/w/:ws/...` routes. `AuthGuard` (cookie `ft_session`, `@Public()` skips) then `WorkspaceGuard` (membership, `@Roles()`); `test/route-guards.test.ts` lists every route, so a new route is covered or the test fails. Input is checked with zod schemas from `@outreach/core/schemas` (422 with `[{path,message}]`). Edits carry `version`; a stale one gets 409 `stale` with `details.current`. Deletes are soft (`deletedAt`) and free the number. Contacts store typed field values (numbers, booleans, `YYYY-MM-DD`), and core rules become Mongo filters in `contacts/mongo-filter.ts` (parity test against core). The sample workspace is seeded per workspace with random free sample numbers (numbers are unique across workspaces).
- **What the screens use:** `GET bootstrap` (everything small), `POST contacts/query|bulk|export`, `GET contacts/lists`, `POST imports` + `GET imports/:id`, `GET/POST sources`, `GET fields/filled`, `POST calls/query` (`contactId` too), `GET calls/:id|live|outcomes`, `GET home`, `POST analytics` + `analytics/export`, `POST campaigns/check`.
- **Knowledge:** web documents and uploaded files (`POST knowledge/upload`, multipart `file`; PDF via pdf-parse, Word .docx via mammoth, text kinds; ≤ 15 MB, kept in `uploads` only until read) are read by jobs. Every ready document is cut into passages (`@outreach/core/chunks`) in `knowledgechunks`; `common/knowledge-index.ts` re-cuts on every text or name change and searches (`POST knowledge/search`, MongoDB text index with the document name ×2 and headings ×3, each word weighted by rarity, BM25-saturated). Embeddings are not in yet (Phase 2). Import report: `GET imports/:id/report` (CSV of every left-out or partly read row, with its file line and reason from core `planImport().problems`).
- **Tests:** `pnpm --filter @outreach/api test` (jest + supertest + mongodb-memory-server, real database, 100k-contact timing). The script sets `NODE_OPTIONS=--experimental-vm-modules`: pdf.js loads its worker with `import()`, which jest refuses without it (plain Node is fine).

### Voice calls: apps/platform-agent (Phase 2, 2026-11-27; local only)

- **Run all of it locally:** `pnpm db:api` (MongoDB 27018), `pnpm dev:api` (4300), `pnpm dev:platform` (3200), `pnpm dev:platform-agent` (the worker; `PLATFORM_METRICS=1` logs each turn's timings). Keys: `apps/platform-agent/.env` (LiveKit, Soniox, ElevenLabs, `ANTHROPIC_API_KEY_EVAL`, copied by name from `apps/agent/.env`) and the same `LIVEKIT_*` + `AGENT_RUNTIME_KEY` in `apps/api/.env`. Locally it uses the `ground-labs` LiveKit project under the agent name `platform-agent-local`: LiveKit only sends it rooms the API asks for by that name, so it never meets outreach or Forktime calls. The platform gets its own LiveKit project when it goes live.
- **A test call:** the editor's Preview → Voice → "Talk to …" (`lib/voice-call.ts`, `components/agent/live-voice.tsx`): `POST /w/:ws/agents/:id/test-call` files a call (`test: true`, the draft snapshotted in `config`), opens room `pf-<callId>`, dispatches the agent with `{kind:"platform", callId}`, and returns a 15-minute browser pass. Test calls show in Calls ("Test call") and are left out of analytics and Home.
- **The agent's door:** `GET /runtime/calls/:id` (setup: draft or published version, filled greeting, the contact's values, `today`, data schema, outcomes, knowledge inline up to 8,000 characters or `search_knowledge` above that), `POST /runtime/calls/:id/events` (batched: line, saved, step, action, ended), `POST /runtime/calls/:id/search`. Public to the session guard, but every request is HMAC-signed (time, one-off nonce, method, path, body hash; 5 minutes, once only): `apps/api/src/common/runtime-signature.ts` ↔ `apps/platform-agent/src/api.js`, with a cross test.
- **How a call runs:** the code says the welcome; the model (Haiku 5.5; Claude 5 models refuse `temperature`, so it isn't sent) talks with `callInstructions()` from `@outreach/core/call-instructions`. It calls `note` with each answer; `noteValue()` checks it (Yes/No, numbers, choices, dates) and `nextStep()` (`@outreach/core/workflow-run`) walks the workflow from the top with the saved answers, so early and changed answers just work. Actions run in code (test calls never reach the outside world; real ones say "for the team to do" until Phase 6). The workflow's End is spoken by the code and hangs up; `end_call` is only for calls that can't go on. A call ended any other way gets a one-shot wrap-up (summary, outcome, missing listen-for fields).
- **Check it end to end without a person:** `node apps/platform-agent/scripts/test-call.js [--agent "desk"] [--say "…"]…` signs in as `voice-test@example.com` with the dev code, joins the room, speaks each line with macOS `say` and prints the filed call with reply times. It must subscribe to the agent's audio (it does): with nobody listening, LiveKit never finishes the agent's speech.
- **Speed (2026-11-27):** 3.6–4.4 s from the end of the caller's words to the agent's voice (target 1.2 s). Per turn: turn end 0.75 s, the `note` round 1.0–1.4 s, the reply's first word 0.65–0.8 s, voice 0.3 s. Haiku 4.5 and 5.5 measured the same.

## Gotchas

- Requiring the LiveKit plugins keeps a Node process alive: a one-off script must call `process.exit()`.
- Outside a worker the SDK logger is not set up: call `initializeLogger()` before creating an `AgentSession` (see `scripts/sim.js`).
- `apps/agent/src/agent.js` only calls `cli.runApp` when run directly, so tests can import it.
- Never give the worker an empty `agentName`: without a name LiveKit would dispatch it into every new room of the project, including the Forktime phone agent's calls.
- The env files hold live provider keys copied from forktime-core. Print key names only, never values.
- `FORKMATE_PHONE_KEY` (agent) must equal `FORKMATE_PHONE_KEY` in the backend env behind `FORKMATE_API_URL`: `.env` = staging (`staging-api.forktime.ai`, the staging droplet's `backend-staging/shared/.env`), `.env.prod` = production (`api.forktime.ai`, `backend-prod/shared/.env`). Different keys for the two.
- `pnpm setup` points at the SAME LiveKit project and Telnyx trunk as production Forktime. Fine for test calls to your own phone; real outreach should use its own numbers (ideally its own carrier account).
